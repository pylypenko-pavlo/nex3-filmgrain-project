# Prior art: who has already done what this project does on the NEX-3N

A survey of other people's work, not camera work. Searched: GitHub (repos, issues and PRs under ma1co/*, code search), the Wayback Machine (nex-hack.info wiki), personal-view.com, eoshd, magiclantern.fm, and web search in EN/RU/JA/ZH/DE. All sources checked 2026-10-05.

Related notes: notes/sony-dsp-isa.md, notes/sony-dsp-generations.md, notes/backup-params.md.

## Summary
- **The scalar core of the SA-DSP is already decoded: ma1co's Ghidra plugin `ma1co/SA-DSP`** (2021-08-09, one commit). A full SLEIGH spec of about 90 opcodes, including flag-conditional branches `bfs`/`bfc`, comparisons `cmp.*` and **float ops `fadd/fsub/fmul/fdiv/ftosi/fsito`**. The opcode table in notes/sony-dsp-isa.md (about 25 opcodes) agrees with it and is a subset. **The VLIW part is not decoded there**, so the bundle analysis (12 + 4x13 bits, notes/sony-dsp-isa.md) is not published anywhere else.
- **Three more ma1co repos are directly relevant:** `ma1co/qemu` (BIONZ emulator with a `cxd4132` machine), `ma1co/OpenMemories-CI` (CXD4132 tests on DSC-QX10 firmware) and `ma1co/OpenMemories-Symbols` (`av-cam.bin` symbols for **DSC-HX20 v1.01, also CXD4132**: 218 names including `Backup_read`/`Backup_write`/`Backup_read_setting_attr`, µITRON tasks `tsk20_sdf`, `tsk46_jpeg`, `tsk23_sdf_rec_*`). Plus `OpenMemories-Docs/hardware.rst`, a chip summary table.
- **Nobody has publicly documented Backup subsystem `0x0003xxxx` (colour, tone, NR, styles).** Publicly known are about 10 properties: language, recording limit, PAL/NTSC, model, serial, uptime, video button, RAW compression on a7x. Creative Style matrices, int8 hue tables, tone curves and Soft Focus/Toy Camera parameters are undocumented. Closest: an EOSHD user (2026-04-14) edits Picture Profile and Creative Style via the unencrypted **settings-save .DAT on the a7 IV**, but those are user-facing knobs, not ISP matrices, and the code is unpublished.
- **No one was found changing Sony colour processing at firmware or DSP level.** No PP unlock, "S-Log hack" or gamma hack for NEX/a6000/RX100: Sony-PMCA-RE issues for "picture profile", "gamma", "creative style", "LUT", "tone curve" return nothing relevant. No grain or film-simulation apps among OpenMemories apps (11 apps in the AppList, all utilities).
- Analogues: **Magic Lantern** decoded Canon `.pf2/.pf3` (12-point tone curve, RGB/LAB gamma blocks, matrices; 2015-2016 thread) and emulates Canon processing engines in qemu-eos (`hw/eos/engine.c`). **CHDK curves** applies a curve on the ARM to the RAW buffer in memory rather than editing ISP tables, a direct analogy to a "grain via ARM/libmpr" approach. **Nikon Hacker has no colour patches at all**: only video, NEF/JPEG compression, Star Eater and dark current.

## 7. What to do with this (most useful first)
1. Load `ma1co/SA-DSP` in Ghidra. Run `sa_sftfcs`/`sa_tbox` (Soft Focus/Toy) and compare with `code/isa/sadis.py`; fix `008r` -> `asrs`. Spend the freed time on VLIW.

4. For notes/sony-dsp-generations.md: apply fwtool PR #52 to the 7M4 `BODYDATA.DAT` and look at how Creative Look (FL/IN/SH...) is built, the closest official Sony analogue of a "film" style.

## Sony patent EP2428889 — "RISC processor with a VLIW coprocessor" (found 2026-10-06)

A Sony Corp patent (EP2428889A1, granted B1 2014-04-30; inventors Hirokazu Hanaki, Satoshi Takashima; priority 2010-09-13) describes a RISC core tightly coupled to a VLIW coprocessor - the same shape as the SA-DSP (16-bit scalar RISC + a wide parallel engine, sections 13-17). It is the first public Sony document found that specifies the coprocessor's instruction philosophy. Whether it describes this exact chip (CXD4132) is unconfirmed; the bit layout below does not match our 64-bit bundle one-to-one (see caveat).

Instruction word in the patent (32-bit):
- `[31:25]` opcode (7), `[24:23]` **fmt** = simultaneously-issuable count (00=1, 01=2, 10=4), `[22]` **cf** condition flag, `[21]` **imm** indicator, `[20:19]` **opc** op-class (00/01 ALU, 10 shift/mov/pack, 11 mul/cmp), `[18:15]` **funct** (4), `[14:10]` **rs** (5), `[9:5]` **rt/imm** (5), `[4:0]` **rd** (5).
- **32-register file** (5-bit operand fields); up to 4 instructions/cycle; slots #1 and #3 predecoded for PC increment; RISC in slot #0, VLIW parallelism = fmt-1.
- Prior-art reference inside it: JP 2002-032218 (subroutine-based VLIW invocation).

Why it matters: it independently confirms what the corpus statistics suggested - a **32-register file** (our slot `a`/`b` fields span all 32 values, 13.4/17.0) and an opcode split into a small class field plus a function field (our `op3` is only the class-sized part). It names the conditional-execution flag (`cf`) and immediate indicator (`imm`), which we had no names for.

**Caveat (honest):** our observed bundle is 64-bit = 12-bit S0 + 4x13-bit slots (section 16), not 4x32-bit. The 13-bit slot (op3.a5.b5) is far smaller than the patent's 32-bit instruction and holds only two 5-bit operands, not three. So CXD4132's SA-DSP uses a more compressed encoding than the patent's reference design; the patent is strong architectural guidance (register count, field roles, coissue model), not a drop-in decoder. Next: check the patent family / same inventors for a variant matching the 64-bit bundle, and test whether a 2-operand compressed form of {opc,funct,rs,rd} fits our 13-bit slot.

### Patent search outcome (consolidated)
US counterpart **US9841978B2** (same inventors, same 2011-07-22 filing) was also checked. Neither the EP nor the US document gives the concrete `funct` table, the NOP bit pattern, or example instruction encodings - patents describe the architecture, not the proprietary opcode map. No SDK, toolchain or symboled ELF for the SA-DSP was found anywhere.

What the patent family does give, as architectural guidance:
- a **32-register** coprocessor file (confirms the corpus inference, 13.4/17.0);
- the coprocessor **operation classes**: `ALU_X`, `ALU_Y`, `BSF` (bit shift), `MOV`, `PACK`, `MPY` (multiply), `CMP_X` - about seven classes;
- named control bits `cf` (condition flag) and `imm`;
- `Vliw_LD`/`Vliw_ST` - the VLIW coprocessor loads/stores through the RISC data cache (so constants/pixels reach the datapath via these, not via immediates inside a bundle - consistent with 13.0).

**Hypothesis (unproven):** our 3-bit `op3` (eight values, with 0 idle-capable and 7 fill) plausibly selects the **operation class**, not a full opcode - the ~7 patent classes map closely onto the eight op3 values, and op3=3's fixed r24 operand would fit a MOV/accumulator-class op. The remaining opcode/funct detail would then live in S0 (which correlates with the slot ops, 17.1) or a per-class reading of the 5-bit fields. This stays a hypothesis: the patent's 32-bit flat instruction does not match our 64-bit 12+4x13 bundle, so CXD4132's SA-DSP is a more compressed, different encoding; without the funct table or an I/O pair the class-to-arithmetic mapping cannot be fixed.
