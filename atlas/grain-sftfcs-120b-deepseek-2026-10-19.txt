## Q2. Key question

NO — the 16x downsample is not shown as a scalar-configurable geometry/stride/scale field in `0x40000..0x40020`; those nine values are fixed local-memory addresses/bounds derived only from the 0/1 stage index and constants.

FACT: The nine values written to `0x40000..0x40020` depend only on `T` from `0x1e38`/`0x1e30`, i.e. on the stage index `r9` and constants `0x0301`, `0x0420`, `0x0430`, `0x0440`, `0x0448`, `0x044c`, etc. They do **not** depend on tile width/height, image size, stride, or descriptor fields.

FACT: For `T=0x17`, the port values relative to `T<<11 = 0xB800` are:

`0x000, 0x200, 0x300, 0x3FF, 0x41F, 0x42F, 0x43F, 0x447, 0x44B`

That is not a geometry like 64x32 or 4x2. It is a sequence of small local-SRAM offsets/bounds.

INFERENCE: This offset sequence is consistent with a fixed multi-level buffer cascade / downsampling pyramid baked into the VLIW microprogram or its memory layout, e.g. several successively smaller local buffers. Changing these addresses would only relocate those buffers; it would not change the 16x downsample ratio or produce full-resolution output.

## Q3. Other levers

(a) Writable full-res operand/buffer address: **Not shown.** Listing A only writes the nine local-memory ports from `struct+0xb4..+0xd4`. No full-resolution engine output/operand address is written in this block.

(b) Real input-pixel address: FACT: Listing A leaves `r5 = [struct+0xa4] - 2` live before `bl r2` at `0x1412`. Listing E sets `struct+0xa4` from table `0x1e10` or `0x1e18`: values are `0x0a/0x0c` or `0x10/0x12`, so `struct+0xa4 = T'<<11`. Therefore `r5` is one of `0x4FFE`, `0x5FFE`, `0x7FFE`, `0x8FFE`. INFERENCE: that range looks like engine-local SRAM, not a DRAM full-resolution image pointer. Changing it moves the local input tile, not the downsample ratio.

(c) Blend/mix/gain/readback: No blend or gain weight is written to `0x40000..0x40020` in Listing A. Listing D writes control ports `0x48208 = 0x10000` and `0x48200 = 0xfffeffff`, but from the shown code these are control/status writes, not a pixel blend weight. No code in the shown windows reads back the 4x2 engine output; that consumer, if any, is outside the provided range.

## Q4. Additional window

Nothing in the shown windows makes the 16x downsample configurable; the only engine-facing values are local-memory addresses/bounds.  
Definitive proof/gainsay requires the VLIW microprogram/command table selected by `run_engine r0 = r4 = 0x1c`; that table is not present in the shown text. If forced to name the next-most-informative shown scalar window, ask for `0x143e..0x1588`, but that still will not directly reveal the microprogram’s downsample ratio.

VERDICT: NO - The 16x downsample is not a scalar-configurable geometry/stride field in the shown `0x40000..0x40020` ports; those are fixed local-memory addresses/bounds derived only from the 0/1 stage index.
