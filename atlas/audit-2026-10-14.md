# Meta-audit — re-check of every negative/blocked/dead grain conclusion (2026-10-14)

Skeptical outside re-audit of the "film grain in the SOOC JPEG" project, in the spirit of the
E-0077 catch (a FALSE NEGATIVE from editing dead filler 0x260 B past live code). Mandate: hunt for
more conclusions of that shape — tests that were methodologically unsound, not facts.

Scope: NEX-3N fw 1.00 / CXD4132, owner's own hardware, authorized interoperability RE (EU Directive
2009/24/EC Art. 5(3)/6). **100% OFFLINE, analysis only, no binary modified.** Every byte/offset below
was re-derived firsthand with `~/nex3n-dump/.venv/bin/python ~/nex3n-dump/sonygen/isa/{sadis,vdump}.py`
on `sa_yknr.bin` (md5 `54acf2988273c0a1f98afc9940f34d60`; the `safeboot/out3n/...` and `sonygen/sa/3N_p8/`
copies are byte-identical — both md5 `54acf298`).

## TOP-LINE (read first)

**Yes — grain is modestly MORE reachable than the current "blocked on every route" standing claims.**
The VLIW route was not closed by a sound negative; it was closed by **two underpowered / mis-targeted
probes (E-0079)** that never touched the code region that actually produces the output. And the scalar
"no per-tile source" verdict is contradicted by the project's own E-0078 result.

The single most valuable fact this audit adds, firsthand: the bundles between **`0xcc38` and `0xce80`
are 73 consecutive VLIW bundles with ZERO idle slots** — dense, live `op3`-stream / `op6`-clamp /
`op5`-AGU / `op7`-accumulate code (the output/DMA-stream finalize program). **No probe has ever landed
in it.** E-0077 edited dead filler at `0xce80`; E-0079 edited two tap-sum bundles at `0xcbf8`/`0xcc30`
upstream of it. The real output store lives in the untested dense block.

**Three highest-value re-tests (all one reversible `/setting` flash, revert = stock md5 `54acf298`):**
1. **The §1a AGU-store-force probe, finally run** — perturb the store/AGU word at **`0xcc38`**
   (`f1c78f000701c000`) and its siblings `0xcc40/0xcc50/0xce78` in the dense block; a flat-grey wall that
   goes flat/black/clipped pins the output store. This is the decisive VLIW test `grain-injection-design.md`
   itself recommended and that E-0079 skipped. (FN-1.)
2. **Re-seed the scalar stub from the ring descriptor, not r13** — E-0078 already proved a 16-B scalar
   stub can READ the per-tile-unique DMA descriptor address at `0x91f0+idx<<4` and land it in the JPEG.
   That address is the per-tile-varying source E-0079 declared absent (it only tried r13, which
   ping-pongs between 2 values). (FN-2.)
3. **A read-control at the E-0074 canvas hook** — `ldr` from the resolved base r0 and exfil it; separates
   "canvas mapped read-only" (E-0074's claim) from "ARM never holds a valid canvas address" (unmapped /
   bad pointer), which the all-writes evidence cannot distinguish. (FN-3.)

## 2. SUSPECTED FALSE NEGATIVES — ranked (the valuable section)

### FN-1 — "r19 is NOT the output luma / the VLIW output is unreachable" (E-0077→E-0079). **HIGH confidence this is a false negative.**

This gates the ENTIRE VLIW grain route (demotes A4/A7 in `grain-angles-overview.md`, closes
`grain-injection-design.md` Task 1, is the "standing gap" cited everywhere). It rests on E-0079's two
corrected r19×2 probes. **Both are unsound, for three independent reasons, all verified firsthand:**

**(a) The probed bundles have FOUR parallel writes to r19 — an ×2 edit on one slot is uninformative.**
vdump, firsthand:
```
00cbf8 1f1f59fa4e1e70d3   S1=7.21.19  S2=7.20.19  S3=4.07.19  S4=4.06.19   (dst=b=19 in ALL four)
00cc30 1f7f59fa4e1e70d3   S1=7.21.19  S2=7.20.19  S3=4.07.19  S4=4.06.19   (same four, S0 idle)
```
E-0079 changed **S4** (`4.06.19` = op4 r6→r19) to `op7 r19→r19` and predicted "luma ×2 → clip white."
But this is a tap-sum finalize: op7=accumulate, op4=mul-accumulate, all four targeting r19. Replacing
one tap's source (r6) with r19 does **not** double luma — it changes the accumulated sum by
`(r19 − op4·r6)`, a small perturbation that the downstream op6 clamp can swallow. (If instead the four
"r19" are four SIMD lanes, the edit brightens ~25 % of pixels — also invisible to a "grey wall stayed
grey" eyeball check with no pixel analysis.) **Either way, a null result does not refute "r19 is on the
output path."** The test lacks the power to detect a true positive.

**(b) `0xcc30` was mislabeled "dead (past terminating NOP `0xcc20`)" — it is LIVE** (a re-commit of the
exact E-0077 offset trap). The NOP bundle `1f70fb87dc3ee1f7` at `0xcc20` is an **intra-program** basic-block
separator — the identical NOP appears mid-program at `0xcab0`, `0xcb10`, `0xcb18`, `0xcb30`. Dense active
code continues well past it (`0xcc28`, `0xcc30`, `0xcc38`, then the whole `0xcc38..0xce78` block). So the
"5 NOP-delimited clusters, cluster 5 = `0xc9f8..0xcc20`" segmentation over-segments; the real P4 program
runs dense to ~`0xce78`. `0xcc30` is inside it.

**(c) The decisive probe was never run.** `grain-injection-design.md` §1a itself names the right test —
"force the `f1c78f00…` store/AGU word at `0xcc38`" — and E-0079 ran only the two r19×2 edits instead.

**Cheap exact re-test (one `/setting` flash each, reversible):**
- **Primary:** perturb the store/AGU word at **file `0xcc38`** = `f1c78f000701c000`
  (`op3 r24→r30 · … · op6 r0→r14 · 0`). Zero the op6 clamp source or redirect op3's `a=24` stream to a
  known-constant reg; shoot a flat mid-grey wall. Tile goes flat/black ⇒ this word feeds the DMA-out store.
  Binary-search 3–4 candidates (`0xcc38`, `0xcc40`, `0xcc50`, `0xce78`) in ≤4 flashes.
- **Secondary (clean r19 test, done right):** target the **single** late r19 write at file `0xce18`
  (`f00787cc07e5bed3`, S4 = `7.22.19` = op7 r22→r19, the "last kernel write", inside the dense live block)
  — add an op7 r19→r19 in a genuinely idle lane of a *neighbouring* bundle that only reads r19, so the edit
  is a clean post-accumulate double, not a tap swap. If the wall blows white, r19 IS on the output path and
  the whole "VLIW unreachable" standing claim is void.

### FN-2 — "the scalar stub has NO per-tile-varying source" (E-0079). **HIGH confidence false negative; contradicts E-0078.**

E-0079 hashed **r13** (`mul r13,r13; mvn`) and got uniform dots → concluded scalar can only write uniform
marks. But r13 is the output tile window, which **ping-pongs between just two values** (`0x9000`/`0x9800`)
— hashing 2 inputs looks uniform by construction. **That is a property of r13, not of the hook.**

Two per-tile-UNIQUE sources are available at the same hook and were not tried:
1. **The ring descriptor address.** E-0078 PROVED a 16-B stub reads `0x91f0+idx<<4` (the ring entry that
   holds **this tile's unique frame destination address**) and lands it in the JPEG. That address advances
   per tile across the whole frame — it is exactly the aperiodic per-tile seed E-0079 said did not exist.
   **E-0078 and E-0079 are in direct tension; E-0078 wins** (it is a positive on-camera result).
2. **Callee-saved r8/r9 at the hook.** Firsthand disasm of the per-tile epilogue (core-0 overlay, text-rel):
   ```
   dd4:  ldr r1,[pc,#28] ; =0x348c        dd6:  str r9,[sp,#8]    <- r8/r9 live, one instr before the hook
   dd8:  bl r1                            dda:  add sp,#80         <- HOOK (chunk+0x2fa)
   ```
   r8/r9 are callee-saved (survive the final `bl`) and are used as per-tile DMA descriptor pointers through
   `0xdd6`. They carry per-tile-varying pointer values at the hook; r13 is merely the easiest-to-grab one.

**Cheap exact re-test:** the E-0078 D2 stub, but instead of splatting the ring word, use it (or r9) as the
LFSR seed: `seed = [0x91f0+idx<<4]`, `mark = hash(seed)`, `str mark,[r13-0x800]`. Dots will now vary per
tile ⇒ per-tile source confirmed. (This does not by itself defeat the 16-B loop ceiling for *per-pixel*
grain, but it removes one of the two stacked blockers E-0079 asserted and makes the sparse-speckle fallback
aperiodic.)

### FN-3 — "the imaging canvas is mapped READ-ONLY for CPU1" (E-0074). **MEDIUM confidence the MECHANISM is unproven** (the practical "ARM can't inject" stands).

E-0074 (EXP-9/10/11) and E-0072/73 are **all writes**. A write data-abort at the resolved base
`DRAM_A+off` is consistent with two different facts: (i) the page is mapped read-only (E-0074's claim), or
(ii) ARM never holds a VALID directly-addressable canvas pointer — the canvas is "handle-only on ARM"
(C-MEM-020), so the `adds r0,r0,r1` reconstruction at the high-ISO YKNR path may yield an **unmapped / wrong**
address that aborts on any access. **No experiment did a READ at that same resolved r0** to tell these apart.
This matters because E-0074's own avenue (c) ("find another writable alias of the canvas") is only worth
pursuing if the mapping is genuinely read-only; if it is just a bad/absent address, alias-hunting is futile.

**Cheap exact re-test:** at the EXP-9 post-completion hook, before the write, `ldr r5,[r0]` and exfil r5
(store to the known-writable `0xD…` scratch E-0071 proved mapped, or via the exfil IPC). Read succeeds +
write aborts ⇒ truly read-only (E-0074 mechanism confirmed). Read ALSO aborts ⇒ the address is
unmapped/wrong and "read-only canvas" was never established.

### FN-4 — "no module file space for a noise tile / module-grow blocked" partly rests on an UNVERIFIED limit. **LOW-MEDIUM.**

The "**~53 KB senser writeFile limit**" (`grain-angles-overview.md:9`) appears **once**, asserted with no
establishing experiment — and the number is just the module's own size (53508 B). No E-record probes the
real senser writeFile maximum. `grain-injection-design.md` §4 then concludes "no free space to bake a 1024-B
noise tile." If the true writeFile cap is larger, a noise tile (pure data, DMA-in source — not executed
code, so the "no in-module loader" blocker does not apply to it) could be **appended** past the current text,
re-opening the A7 DMA-LUT grain-source path.

**Cheap re-test (no flash risk):** senser `writeFile` a deliberately-oversized (e.g. 96 KB) scratch file to
`/setting/` and read it back; confirms the actual cap. (Separately, whether the On-Demand Loader will load a
grown `sa_yknr` past its descriptor length is a second question — but the cap itself is settleable in one
no-capture senser session.)

## 3. ERRORS FOUND (with corrections)

- **E-0079 mislabels `0xcc30` as dead.** `0xcc20` is an intra-program NOP (same bundle at `0xcab0/cb10/cb18/
  cb30`); `0xcc30` is live code inside the dense `0xc9f8..~0xce78` P4 program. (Same offset-trap family as
  E-0077, re-committed inside the correction.) → treat `0xcc30`'s null as uninformative, not confirmatory.
- **The "5 NOP-delimited VLIW clusters / cluster 5 = `0xc9f8..0xcc20`" model over-segments** (`grain-injection-
  design.md` §0b). NOP bundles occur mid-program; the P4 program is dense to ~`0xce78`. The `0xcc38..0xce80`
  region (73 bundles, **0 idle slots**, firsthand) is live, not "coefficient tail." Only `0xce80+` (the
  `8fff…/bfff…/b54f…` ff-filler) is dead.
- **`dsp-read-trick.md:212` still says "`b` ±0x2000 range."** Stale — corrected to ±0x1000 in
  `grain-codecave.md` and firsthand here. (The local conclusion there, `0x3800 > range`, survives either
  value, so nothing downstream breaks — but fix the number for consistency.)
- **"~53 KB senser writeFile limit" is an unverified assumption** stated as fact (see FN-4).
- Minor: `engine-command-table.md` / `dsp-read-trick.md` D5 still describe "Region B = inline VLIW program"
  at `0xbf34/0xbfa8`; `grain-injection-design.md` §0a already corrected this to a scalar wrapper + literal
  pool. Propagate that correction (those two docs still read as if Region B VLIW is real).

## 4. MISSED ANGLES (not yet tried)

1. **Probe the dense `0xcc38..0xce80` block at all.** It is the most likely home of the real output-luma
   store (op5/AGU → SRAM `0x9000`) and has never been edited. FN-1's §1a force-probe is the entry point.
2. **Seed a scalar grain/speckle stub from the ring descriptor address** (per-tile-unique, E-0078-readable)
   instead of r13 — turns Probe-S speckle aperiodic and unblocks any seeded loop. (FN-2.)
3. **Read-control at the E-0074 canvas hook** — disambiguates read-only vs unmapped. (FN-3.)
4. **Settle the real senser writeFile cap** — one no-flash senser session; if > ~53 KB, a baked noise tile
   (A7 DMA-LUT source) becomes possible. (FN-4.)
5. **E-0078 §0 did not sweep the documented SA candidate ARM windows** (Q-29/Q-30, C-SYS-006/007 — named in
   `dsp-read-trick.md` §0 point 3). It swept only `0x91f0`/mirrors/`0x9000`. A low-cost no-flash completeness
   check before accepting "no ARM aperture to DSP SRAM."
6. **The "GO bit transient" reading (E-0078)** is plausible but assumes the stub's `0x91f7` hit the live ring
   at the epilogue; a black (0x00) splat is also consistent with reading a wrong/stale `idx` base. Not
   load-bearing (static "6 descriptors" fallback), but worth one confirmatory address-sweep splat if the
   ring extend (`#6→#7`) is ever pursued.

## 5. One-paragraph standing after the audit

The colour half remains solid and shippable. The grain "blocked on every route" verdict is **too strong**:
it rests on E-0079, whose VLIW probes were underpowered (4-way-write bundles, wrong offset re-committed) and
whose scalar "no per-tile source" is contradicted by E-0078. The dense, live `0xcc38..0xce80` VLIW block —
73 idle-slot-free bundles that almost certainly program the output DMA store — has never been touched. Grain
is not proven reachable, but it is **not** soundly proven blocked either; the honest state is "the decisive
VLIW output probe was never run." Run FN-1's `0xcc38` force-probe next — one reversible `/setting` flash — and
re-seed the scalar stub from the ring descriptor (FN-2). Both are cheap, both directly attack conclusions this
audit found unsafe.
