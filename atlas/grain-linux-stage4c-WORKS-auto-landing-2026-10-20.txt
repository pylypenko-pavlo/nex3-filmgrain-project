THE ONLY BLOCKER WAS THE FINAL WRITEBACK: Fsys_Rename(tmp,path) is a PrFILE veneer and fails even with the dest
removed (lnx RE: the low-level rename forwards to an external PrFILE op, unreliable in this Fsys config) ->
ABANDON rename. FIX (proven primitives only, all observed working this session): after the grained .TMP exists,
  Fsys_Remove(path); Fsys_Open(path,0x7)+Fsys_Write+Fsys_Close   (0x7 = the firmware's capture-create flags).
This is the identical sequence the firmware uses for every photo. Fsys_Open @0x143fd, Write @0x16cd9, Close
@0x11d01, Remove @0x154b9 [VERIFIED].

FINAL SHIM (code/grain-shim/grain_hook.c, md5 e9ac0d9e4dc181fd1151866170247582) design for the ~45MB-Linux / 388KB-1MB-free / slow-SD camera:
  PHASE 1: read the whole source JPEG into a RAM buffer (one sequential read -> no 4KB SD read/write interleave,
    which was the callback version's "long hang"); streaming-decode from RAM (92KB scratch) + grain (row-stream,
    ~0.4MB) + streaming-encode via write_cb to a ".TMP" (Exif APP1 spliced in the first header chunk). The
    ORIGINAL IS NOT TOUCHED -> a watchdog reboot during the slow codec loses nothing.
  PHASE 2 (land): read the grained .TMP back into the freed RAM buffer, validate SOI, then Remove(orig) +
    Open-create(orig,0x7) + Write + Close; Remove(.TMP) on success. The .TMP is the on-disk backup through the
    tiny remove->write window -> power-loss safe (grained image recoverable from .TMP).
