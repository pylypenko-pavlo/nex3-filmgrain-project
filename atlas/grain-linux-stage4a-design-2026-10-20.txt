1) Fsys_Close SIGNATURE + PATH RETRIEVAL
======================================================================
From libInfraFsys.so disasm (Thumb) + its own debug format strings [VERIFIED]:
- Fsys_Close @0x11d01: debug fmt @0x11e81 = "Fsys_Close - %p" -> ONE arg, r0 = the file HANDLE
  (opaque pointer/token). Prologue `push {r0,...}; sub sp,#0x40` saves arg0 at [sp+0x40] and reloads
  it; the handle is resolved INTERNALLY (blx 0xdb24) to a file-object, then a field is read via an
  internal helper (0x11d4c: `ldr r1,[pc+..]; ldr r0,[sp+0x3c]; adds r0,r0,r1; blx 0xd914`).
  => the PATH is NOT an argument of Fsys_Close and is reachable only through non-exported internal
     helpers (0xdb24/0xd914) at load-base-relative addresses — NOT safely callable from a shim. [VERIFIED]
- Fsys_Open @0x143fd: debug fmt @0x14711 = "Fsys_Open - %s, %p, 0x%08lx" -> arg0 (r0) = PATH (%s,
  const char*), arg1 (r1, %p) = an OUT pointer (zeroed at 0x14450 `str r4,[r0]` then filled), arg2
  (r2) = flags, arg3 (r3) = mode. A full-body scan shows NO caller stack args (no [sp>=0xa8] access)
  -> Fsys_Open has <=4 register args, so a 4-arg C interposer forwards r0-r3 exactly. [VERIFIED]
RESOLUTION: the path is NOT at Fsys_Close; it IS at Fsys_Open (arg0). So the design records
(handle -> path) at Fsys_Open and matches it at Fsys_Close. [VERIFIED path@Open; the handle key =
*arg1 after a successful open is an ASSUMPTION — arg1 is the written out-pointer — to be confirmed in
the zero-brick isolation test; a wrong key only loses a log line, never changes behavior.] [OPINION]
Fsys handles are opaque tokens, NOT raw fds (Fsys_Close resolves them internally), so matching, not
raw-fd tricks, is the only route.

======================================================================
RTLD_NEXT DOES NOT WORK on the camera sonyld. Tested in qemu under the real normal sonyld
(df94859e): __dlsym((void*)-1 / 0 / -2 / -3, "close") ALL return 0x00000000. [VERIFIED qemu]
WHAT WORKS: __dlopen("<lib>.so", 1) + __dlsym(handle, "sym"). Tested:
  __dlopen("libsonyc.so",1) = 0x3f7c4800 ; __dlsym(h,"close") = 0x3f728208 (the REAL close). [VERIFIED]
  And it BYPASSES our own interposer: with a preload that itself exports close(), our &close=0x3f7bf438
  while __dlopen("libsonyc.so")+__dlsym(close)=0x3f728208 (the real one). [VERIFIED scope test]
=> 4a resolves the real functions via __dlopen("libInfraFsys.so",1) + __dlsym("Fsys_Close"/"Fsys_Open"),
   cached, lazy, sanity-checked (!= our own address). This is the robust route for ALL future hooks.
Also [VERIFIED]: a preload with UND imports of __dlopen/__dlsym and ZERO DT_NEEDED loads fine (sonyld
resolves its own exports; lazy PLT binding, no load-time failure) — the probe shims proved this.

4a SOURCE SUMMARY (grain_hook_4a.c — builds, proven shape)
======================================================================
- Freestanding, zero DT_NEEDED, raw syscalls (open/read/write/close/lseek). Imports only
  __dlopen/__dlsym (from sonyld). ELF: 2 PT_LOAD + DT_INIT_ARRAY + 1 R_ARM_RELATIVE, exports
  Fsys_Open + Fsys_Close (GLOBAL FUNC). [VERIFIED readelf]
- ensure_resolved(): lazy, once; __dlopen("libInfraFsys.so",1)+__dlsym; drops a self-bind; logs result.
- Fsys_Open(path,outH,flags,mode): calls REAL open (args unchanged), returns its value unchanged; on
  success + is_dcf_jpg(path) records (*outH -> path) best-effort. is_dcf_jpg = suffix ".JPG"
  (case-insensitive) AND "DSC" substring (matches the libmpr DCF template \DCIM\101MSDCF\DSC0%04ld.JPG).
- Fsys_Close(h): calls REAL close FIRST (unchanged), returns its value unchanged; if h was recorded as
  a DCF-JPG, raw-stat the path for size and append "CLOSE JPG <path> <size>" to
  /setting/grain_hook_4a.log. Every non-JPG close is a pure passthrough.
- FAIL-SAFE: real called first + value returned unchanged; logging is additive; if resolution ever
  returns NULL the interposer returns a benign -1 (MUST be proven impossible in the isolation test,
  which logs the resolved pointer, BEFORE any boot-path use). The *outH deref is guarded (success +
  JPG only) and must be confirmed in isolation (a bad deref crashes only the test process).
VALIDATION ORDER (coordinator): build -> qemu (loads, ctor logs "hook loaded", resolution logs OK) ->
  isolated updater-shell test (Task-2 harness: confirm resolution non-NULL + a real JPG open/close logs
  path+size, with ZERO brick risk) -> only then boot-path.

4b / 4c GRAIN FLOW SKETCH (design only) + THE ALLOCATION PROBLEM
======================================================================
After the real Fsys_Close returns, the JPG is complete on disk. Grain flow:
  1. Re-open + read the JPG bytes (raw open/read on the path -> a src buffer), OR keep in memory.
  2. DecodeStillOnMemory (MprIf @0x5d52bc -> MprLibCore @0x174be0): 8-field VA/size param block
     [dstVirtAddr, maxDstSize, srcVirtAddr, srcSize, sizeX, sizeY, resultWidth, resultHeight] — decode
     JPG(srcVirtAddr,srcSize) -> pixels at dstVirtAddr. Output = single contiguous YUV buffer (log
     "[MprLib] Dst YUV Address : = <a> , Size = <n>"). [VERIFIED entry disasm + strings]
  3. Add signed noise to LUMA: runtime-detect layout from Size/(w*h): ==2 -> packed YUYV 4:2:2, Y at
     even bytes (0,2,4,...); ==1.5 -> planar 4:2:0, Y = first w*h contiguous bytes. Clamp 0..255; leave
     chroma untouched. [OPINION/strong — format per C-MEM-005; confirm at runtime via Dst Size]
  4. EncodeStillOnMemory (@0x5d53f8 -> MprLibCore @0x174bf0): [srcVirtAddr, srcSizeX, srcSizeY, dstSizeX,
     dstSizeY, dstTgtSize, dstBufVirtAddr, dstBufSize] -> re-encoded JPG at dstBufVirtAddr.
  5. Overwrite the file (raw open O_WRONLY|O_TRUNC + write, or Fsys_Open/Write/Close).

THE ALLOCATION PROBLEM (the hard part — flag for 4b/4c):
- DecodeStillOnMemory needs a dst PIXEL buffer. Full SOOC is ~16 MP; 4912x3264x2 (4:2:2) ~= 32 MB.
  EncodeStillOnMemory needs a dst JPG buffer (several MB). WHO allocates these in-shim?
  (a) libc malloc via __dlopen("libsonyc.so")+__dlsym("malloc") — a 32 MB malloc per shot in the appFw
      heap; may fail/fragment; adds a libc dependency path. [OPINION]
  (b) raw mmap(MAP_ANON) ~32 MB on demand, munmap after — no libc, clean, PREFERRED; needs the JPEG
      dimensions first (parse the SOF0 FFC0 marker for w,h to size the dst). [OPINION, preferred]
  (c) static 32 MB BSS scratch — bloats memsz and reserves 32 MB resident in EACH of the ~6 preloaded
      processes -> wasteful / OOM risk. [reject]
- DECODE needs dst size BEFORE decoding -> parse the JPEG SOF for w,h, allocate w*h*2, then decode.
- TIMING/SYNCHRONY: this is heavy work done SYNCHRONOUSLY inside Fsys_Close (decode+grain+encode+rewrite
  per shot). If the codec is HW-assisted/fast (Q-11 indicators: ioctl DMA_TRANSFER_MEM, likely fast) a
  ~100-300 ms close delay is tolerable; if slow, it risks a watchdog/UI stall. -> MEASURE decode+encode
  time in the isolated test first. If too slow for the close path, the grain belongs in a different
  hook (e.g. a post-save worker), not Fsys_Close. [OPINION]
- RECOMMENDATION: keep 4a (detection) in Fsys_Close; prototype 4b (decode->re-encode->rewrite) with
  mmap-anon buffers, first in the ISOLATED updater-shell test on a sample JPG (zero brick risk, measures
  time + proves the decode/grain/encode chain), BEFORE moving grain into the boot-path shim.

BOTTOM LINE 4a: Fsys_Close sees only the handle (path not an arg); Fsys_Open sees the path (arg0,
VERIFIED). Both are PLT imports from libmpr/libObj (VERIFIED), so the preload interposes them. Real
symbols resolve via __dlopen+__dlsym (RTLD_NEXT is dead on this sonyld — VERIFIED). The 4a source is
fail-safe detection-only and built. The grain itself (4b/4c) hinges on buffer allocation (prefer
mmap-anon) and decode/encode timing, both to be measured in the zero-brick isolation harness first.
