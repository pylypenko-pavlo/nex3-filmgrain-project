======================================================================
TASK 2 — ISOLATED ON-CAMERA PRELOAD TEST (zero brick risk) -> FEASIBLE.
======================================================================
Findings [VERIFIED from the dump]:
- The updater busybox is DYNAMIC: `bin/busybox` interp = /lib/libsonyld.so; the p1 updater initrd
  ships /lib/sonyld.so + the full camera libc (libsonyc.so, libsonystdc++, libsonypthread, ...).
  => the updater shell runs real camera binaries through a real sonyld.
- The updater sonyld (p1, md5 850db922fe51836e3c25bf0e07d4dd1c) DIFFERS from the normal/Stage-3
  sonyld (p3, md5 df94859e...). A plain `LD_PRELOAD=... busybox` tests 850db922. To test the
  Stage-3-relevant df94859e, place it on /setting and run a dynamic binary whose PT_INTERP points
  at it (below). BOTH builds accept our object in qemu (df94859e exit 0 + ctor; 850db922 exit 0).
- Updater vfat mount opts (common.src) = "posix_attr,rw,nodiratime,noatime,shortname=mixed" — NO
  `noexec` -> binaries on a mounted /setting are EXECUTABLE. /ramdsk (tmpfs) also available. busybox
  has mount/cp/cat/ls. [VERIFIED]

qemu simulation of the EXACT on-camera command (normal sonyld df94859e placed at a /setting path,
invoked via a zero-dep dynamic binary dyntest whose interp = that sonyld):
  baseline  qemu /setting/dyntest                              -> exit=0
  LD_PRELOAD=/setting/grain_probe_fs.so qemu /setting/dyntest  -> exit=0 (ACCEPTED, ctor ran) [VERIFIED]
  LD_PRELOAD=/setting/bad.o            qemu /setting/dyntest   -> "unsupported file type", exit=1 [VERIFIED]
This is the exact pattern the updater shell would run, proven to accept/reject correctly against the
normal sonyld.

ISOLATION (why it CANNOT brick) [VERIFIED by process model + the controls above]:
- The test runs as a CHILD process inside the ALREADY-BOOTED updater. If the preload fails to load,
  sonyld _rtld_die exits ONLY that child (nonzero); the updater shell (parent) and init survive — the
  controls (bad.o/junk) killed only the child, the shell kept running. A preload failure here never
  touches the boot path. This is categorically different from Stage 3 (preload in init's boot-critical
  children). ZERO brick risk.

EXACT on-camera command sequence (run from the pmca updater shell, sh(be,[...])); all READ-ONLY to
flash — it only reads /setting files and execs in RAM:
PREP (host): put three files on /setting via senser cam.writeFile (or the updater shell after mount):
    /setting/grain_probe_fs.so   (our gold object, built in-VM, md5 to be recorded)
    /setting/sonyld_norm.so      (= the NORMAL p3 sonyld df94859e, copied from the dump)
    /setting/dyntest             (zero-dep dynamic ELF, PT_INTERP=/ramdsk/sonyld.so, built in-VM)
TEST (updater busybox):
  sh(be,[
    'mount -t vfat /dev/nflasha2 /setting -o rw',
    'mkdir -p /ramdsk && cp /setting/sonyld_norm.so /ramdsk/sonyld.so',
    'cp /setting/dyntest /setting/grain_probe_fs.so /ramdsk/',
    'rm -f /setting/grain_probe_fs.log',
    'LD_PRELOAD=/ramdsk/grain_probe_fs.so /ramdsk/dyntest ; echo EXIT=$?',   # <- the decisive line
    'cat /setting/grain_probe_fs.log 2>&1',                                  # ctor proof (if the ctor logs here)
    'umount /setting',
  ])
  (dyntest built with PT_INTERP=/ramdsk/sonyld.so so the NORMAL sonyld is the loader, and everything
   runs from the exec-capable /ramdsk; /setting needs no noexec workaround but /ramdsk is belt-and-braces.)
INTERPRET:
  EXIT=0 and NO die-string on the console  -> the camera's REAL normal sonyld ACCEPTS grain_probe_fs.so
      on real silicon. Combined with Task 1, the Stage-3 load-failure brick cause (C-LNX-012) is reduced
      to near-zero. [this is the prize]
  Any die-string ("wrong number of segments"/"unsupported file type"/"unrecognized file format2") +
      nonzero EXIT -> the object is rejected on real silicon; DO NOT proceed to Stage 3; fix the object.
BONUS (tests the updater's own 850db922 too): `LD_PRELOAD=/ramdsk/grain_probe_fs.so busybox echo OK`.

SCOPE/CAVEATS:
- This proves sonyld's LOAD/relocate/ctor acceptance — exactly the brick cause (a failed LOAD is fatal,
  C-LNX-012). sonyld's map_object is per-object and host-process-independent, so a load that succeeds in
  dyntest succeeds identically in im.elf/the appFw tree. [OPINION, strong — same object, same loader]
- It does NOT exercise the grain HOOK under the real appFw (runtime behavior); but hook misbehavior is
  not a boot-brick (it would at worst corrupt a JPEG / crash the app process, recoverable), whereas a
  LOAD failure is the unrecoverable brick this test targets.
- Two sonyld builds exist; the /setting/dyntest path tests the Stage-3 one (df94859e). Run both for
  completeness.

BOTTOM LINE: qemu is faithful (Task 1 VERIFIED). An isolated, zero-brick-risk on-camera test of
grain_probe_fs.so against the REAL sonyld IS feasible from the updater shell (Task 2 VERIFIED, exact
commands above). Passing it on real silicon would nearly eliminate the Stage-3 load-failure brick risk
BEFORE any boot-path preload. It still does not create a recovery NET for a Stage-3 failure (see
brick-recovery-analysis.txt) — it lowers the probability of the failure, it does not make a failure
