================= DEEPSEEK CROSS-CHECK on the 388KB-free memory (2026-10-20) =================
1. The 11MB working set thrashed because it was ~10.6MB OVER free -> ~2600 code-cache pages reclaimed and
   re-faulted from flash repeatedly during the long decode = severe thrash = the long hang. Streaming I/O drops
   the working set to ~0.4MB = only ~12-22KB OVER the 388KB free -> ~3-8 pages reclaimed ONCE (scratch allocated
   once + reused) -> trivial, "unlikely noticeable thrash". => streaming I/O should fix the SPEED. The residual
   per-shot cost is just the ARMv5TE codec itself (inherently multi-second on 16MP), which the owner accepted.
2. If still tight, shrink the grain scratch (~0.4MB) further, biggest-win first: (a) 8-bit rings for the hblur
   noise (half); (b) chroma as a single pass with the 13-tap KC=K*K kernel instead of 2x7-tap (fewer rings);
   (c) sequential Cb-then-Cr reuse. [Column-tiling, DeepSeek's top idea, does NOT fit our full-width row-band
   streaming — skip it.] All require a bit-exact re-validation. Likely unnecessary since 0.4MB ~= free already.
3. I/O pitfalls to handle: Fsys/page-cache may cache src/temp and re-add pressure (use nocache/drop if available);
   interleaved SD read(src)+write(temp) serialises on the card + triggers erase-block RMW/GC -> use larger
   sequential buffers, avoid fine interleave; keep the .TMP+rename (power-loss safe: original survives until
   rename); the rename failure matches "FS won't overwrite existing / target open" -> close+flush+remove-first.
4. Blunt: viable but marginal; the multi-second pause per shot is inherent to in-process 16MP re-encode on this
   ARM. Alternatives (grain before the camera's own JPEG encode; use the reserved pool; defer to playback) are
   heavier re-architectures -> keep the current approach, accept the pause, make the working set ~= free.

================= RENAME CAUSE + FIX (lnx RE, 2026-10-20) — VERIFIED =================
Fsys_Rename(SOURCE,DEST) @0x1593d: arg order was RIGHT (source=tmp, dest=path). It has NO clobber handling and
goes straight to the PrFILE/FAT rename, which REFUSES an existing destination (EEXIST). DSC#####.JPG already
existed -> <0. No firmware whole-file "replace DCF" API exists (it writes new DSC numbers or patches metadata
in place). FIX (verified): Fsys_Remove(path) BEFORE Fsys_Rename(tmp,path). No flush needed (Close(tmp) commits;
Rename flushes internally). Applied to grain_hook_4c.c. Fsys_Remove @0x154b9, Fsys_Rename flush vtable @0x15a18.
Tiny window where the DCF is absent (remove->rename); power loss there loses the shot (grained bytes survive in
.TMP); low-prob, acceptable. Remove+Rename briefly desyncs the MPR DCF database -> the camera's "recover?" prompt
may appear (harmless; the on-disk grained file is correct). Runner-up (keeps name present, may avoid the prompt,
NOT power-safe): open the ORIGINAL with WRITE|CREATE|TRUNC (flags 0x16, TRUNC bit inferred) and write in place.
